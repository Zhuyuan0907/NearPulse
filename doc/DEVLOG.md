# NearPulse 開發版本過程（DEVLOG）

本文件記錄每個版本的：開發範圍、關鍵決策、與架構討論結論的對應/偏離。

## v0.1.0 —— Walking Skeleton（2026-09-04）

### 目標

以「簡單可行性優先」實作完整縱切：
**回報 → 批次分群 → 兩段式確認 → 事件升級 → 態勢卡 ETag 讀取**，
讓設計討論中的核心機制全部可以在本機跑通、用 curl 驗證。

### 開發範圍（完成）

- **Server（Node + Express，零額外持久化依賴）**
  - 回報 ingest：欄位驗證、UUID 冪等、附件大小防呆
  - 10 秒批次 worker：歸屬（`attachToEventId` 優先 → 同站同類型自動比對 → 開新 candidate）
  - 事件狀態機：`candidate → active → frozen / cancelled`（含否證否決與超時取消）
  - 態勢卡：確定性模板生成、worker 預算、ETag/304 快取
  - AI advisor 三件套（STT/Vision/LLM）：介面 + stub、fire-and-forget
- **Client（React + Vite PWA）**
  - session UUID（sessionStorage，關頁即滅）
  - 位置狀態機 L1/L2/L3（GPS 一次查詢 → session 記憶 → 路網圖手選）
  - 回報頁：四類型大按鈕、歸屬確認（同一件/另一件）、hold-to-talk 語音、照片壓縮、UUID 冪等 + 樂觀 UI
  - 確認頁：兩段式（在場嗎 → 有看到嗎），清單入口 + deep link 入口
  - 態勢卡頁：ETag 輪詢（12 秒、304 沿用、Page Visibility 背景停止）
  - manifest（可安裝 PWA）；刻意不安裝 Service Worker（網路可用假設）

### 關鍵決策與理由

1. **記憶體儲存 + store 介面**：架構要求 Redis/PG，但 walking skeleton
   的目的是驗證資料流。`store/index.js` 工廠模式讓日後換儲存零改動業務層。
2. **態勢卡不經過 AI**：討論結論「LLM 不在關鍵路徑」的直接實作——
   建議文字全部來自 `ADVICE_TEMPLATES` 確定性模板；LLM stub 只產時間線字串。
   這讓 MVP 的降級路徑＝主路徑，天然驗證了設計原則。
3. **推播以「徵詢區塊 + 確認頁」閉環替代**：Web Push 需要 VAPID 金鑰、
   iOS 需加主畫面，且無法 bypass 靜音。MVP 先讓循環跑起來：
   態勢卡 `pending` 區塊 → 點擊 → 兩段式確認 → 門檻 → 升級。
   介面（deep link `#/confirm?event=`）與未來推播完全相容。
4. **語音採「上傳制」**：iOS Safari 無 `SpeechRecognition`（設計討論結論），
   因此 client 只用 `MediaRecorder` 錄製上傳，STT 在 server 端 stub。
5. **零路由依賴**：hash router 30 行自寫，避免 walking skeleton 階段
   引入 react-router；三頁面結構已為未來 code-split（讀取端拆輕量 bundle）預留。
6. **GPS 此版不反查站點**：「座標 → 最近站」需要站點座標圖資，
   v0.1 的 GPS 僅記錄信心資訊，站點由 L2/L3 解析。列為 Phase 2。

### 刻意的簡化（非偏離，是分期）

- 附件（語音/照片）只保存於記憶體事件內，不落磁碟、不供下載
- 態勢卡 `pending` 徵詢為全站廣播式（未依使用者位置過濾——位置聲明在 client）
- `locationClaim.stationName` 由 client 帶站名（server 不持有完整路網）

### 已知問題

- 記憶體儲存重啟即清空（by design，Phase 2 換 Redis/PG）
- 附件（語音/照片）只保存於記憶體事件內，不落磁碟、不供下載
- 態勢卡 `pending` 徵詢為全站廣播式（未依使用者位置過濾——位置聲明在 client）
- `locationClaim.stationName` 由 client 帶站名（server 不持有完整路網）
- 無任何認證：MVP 假設信任模型靠「獨立 session 交叉驗證」，Rate limit 未實作

## v0.1.1 —— 單一埠號模式（2026-09-04）

### 變更

- server 進入點新增靜態檔服務：直接服務 `client/dist`，
  **:3000 同時提供 API 與前端**，單 port 即可穿 Cloudflare Tunnel。
- SPA fallback 回 index.html（hash 路由保險）；未知 `/api/*` 回 404 JSON
  而非落入 fallback。
- `client/dist` 不存在時僅提供 API 並印出提示（不 crash）。

### 部署形態

- 單 port（tunnel 用）：`client build → server :3000`
- 開發（HMR）：server :3000 + vite :5173（/api 代理不變）

## v0.2.0 —— 地下視覺定位與疏散（2026-09-04）

### 目標

把「拍照」從一個沒人看的附件，升級成一條完整的地下定位鏈路：
**前端壓縮 → Vision 辨識視覺錨點 → 回填九宮格 → 算出疏散向量**，
並讓語音之外多一條文字輸入通道。

核心前提：地下沒有 GPS 不是故障，是常態。既然拿不到座標，就用人與相機
都看得見的東西定位——柱號、店名招牌、逃生燈箱——再把結果收斂到九宮格。

### 開發範圍（完成）

- **場域模型泛化**：`stations.js` → `venues.js`，服務對象從捷運站體擴大到
  任何「地下、無可靠 GPS、平面近似矩形」的空間（地下街、地下停車場…）。
  每個場域自帶九宮格出口格位——這份資料同時餵給定位與疏散。
- **九宮格區域（`ZonePicker`）**：點一格完成場域內的最後一哩定位，
  出口格標 🚪，選完即時顯示疏散向量——同一個元件既是定位器也是疏散圖。
- **疏散向量（`evacuation.js`）**：純函式、確定性。以 Chebyshev 距離取
  「離事件最遠的出口」與「該避開的出口」，無資料就回 null 退回通用文字。
- **Vision advisor 接上真實服務**：可插拔 provider 表（`openai` / `none`），
  gpt-4o-mini + `detail: low`。輸出嚴格正規化成固定欄位，非法值收斂成 null/[]。
- **`POST /api/vision`**：拍完照同步分析，回九宮格建議供一鍵套用。
- **文字補充（≤140 字）**：與語音併行的第二輸入通道，同時是不支援錄音時的替代。

### 關鍵決策與理由

1. **Vision 供應商做成可插拔表格**，而非寫死 gpt-4o-mini。原始規格就寫著
   「GPT-4o-mini Vision **或**小型地端 OCR」——那個「或」值得在程式結構裡
   留一個位置。日後接地端 OCR 只需在 `PROVIDERS` 加一個 entry，呼叫端不動。
2. **所有失敗路徑回傳同一個降級形狀**（未設定 / 逾時 / API 錯誤 / 回傳非 JSON）。
   呼叫端無從分辨「AI 沒開」與「AI 掛了」——這正是它永遠擋不住回報的原因。
   e2e 在完全沒有金鑰的環境下 13 項全過，即為此設計的證明。
3. **照片只上傳一次、只分析一次**。`/api/vision` 暫存照片 10 分鐘並回 `photoRef`，
   回報帶 ref 取代 base64；已取得的分析結果隨 `photoAnalysis` 回傳，batch 端
   不再對同一張圖付第二次錢。3G 下省掉一個 50KB 來回。
4. **壓縮要量到達標才算數**。規格寫「<50KB」，所以壓完必須量——
   細節多的場景（地下街招牌、人群）q0.6 常落在 60–120KB，
   因此加了品質階梯 0.6→0.45→0.35，仍超標就降到 800px。
5. **EXIF 方向必須轉正**。柱號、招牌、燈箱全是文字，手機直式拍攝若不轉正，
   送進 Vision 是躺著的——這對 OCR 是災難性的，而 `createImageBitmap`
   預設並不套用 EXIF。一行參數，但它是整條辨識鏈路成立的前提。
6. **疏散建議在資訊不足時不硬給方向**。事件落在正中央 B2 時，四個角落出口
   的棋盤距離全部相等，「往全部四個出口移動」讀起來像建議、實際上是雜訊。
   改為明說「各出口距離相近」——恐慌情境下，誠實比假裝精確安全。
7. **「同一件」不再跳過補充**。原本點「同一件」會直接送出，等於放棄九宮格、
   語音、文字、照片；但「補一筆到既有事件」恰恰常是最需要區域資訊的時候
   （既有事件可能還沒有 zone）。改成先選歸屬、再走補充區，
   點擊數 2 → 3，仍在「3 次點擊完成回報」之內。

### 刻意的簡化（非偏離，是分期）

- 照片暫存在記憶體（重啟即失效）；ref 失效時靜默退回帶完整 base64 的路徑
- STT 仍為 stub——語音上傳路徑已通，但不轉文字
- Vision 的九宮格建議只在「事件尚無 zone」時才寫入，使用者手選永遠優先

### 已知問題

- **`/api/vision` 無認證、無限流**，會直接把請求轉發到付費 Vision API。
  本機與展示環境可接受，**公開穿 tunnel 前必須補上防濫用**（Phase 2）
- `venues.js` 的出口格位是示範資料，正式部署需以實際場勘結果替換
- 九宮格是「近似矩形平面」的抽象；多層站體（B1/B2/B3）目前只能當成不同場域
- 記憶體儲存重啟即清空（by design）

### 順手修掉的既有缺陷

- `cluster.js`：否證規則排在狀態檢查之前，已 cancelled 的事件每個 batch tick
  會被重複「取消」一次——log 洗版，且態勢卡每輪被判髒重算。終態現在提前返回。
- `ReportPage`：「先點類型、後選場域」的順序會整個跳過歸屬確認，
  永遠開新事件。場域確定後補做一次 `fetchEventsContext`。
- `e2e.sh`：vision 檢查把 shell function `json` 包進 `bash -c` 子 shell，
  必然報 `command not found`——這個檢查從加進去就沒有真的驗過任何東西。

## v0.3.0 —— OSM 場域圖資 + 影像九宮格定位（2026-09-04）

### 起因：一個根本的誤解

v0.2 交付後才釐清——**九宮格是「照片的九宮格」，不是「場域的九宮格」**。
它的用途是把 AI 的視線導到照片裡真正能辨識位置的那一小塊（站名牌、出口編號牌），
其餘區塊多半是牆面地板人群，沒有資訊。

而 v0.2 把它實作成場域平面的區域選擇器，並把 Vision 回傳的格位寫進 `event.zone`，
再餵給 `evacuation.js` 當成樓層座標算疏散方向。**兩套座標系共用同一組 `A1`~`C3`
字彙，在同一個欄位靜默合併**——產出的疏散指示結構正確、語氣篤定、方向隨機。
這比幻覺更難發現：幻覺至少會胡言亂語，量綱錯誤只會給你一個看起來很合理的錯答案。

### 開發範圍（完成）

- **場域圖資改由 OSM 產生**：`scripts/build-venues.mjs` 分區查詢 Overpass，
  推導出全台 519 個場域、614 個出口，離線產生 JSON 進版控
- **場域資料搬到 server**：`client/src/data/venues.js` 刪除，client 不再持有任何圖資
- **影像九宮格 ROI**：`PhotoRoiPicker` 疊在照片縮圖上，標出有牌子的那一格
- **Vision 改為兩段式**：`locate`（找那一格）→ `read`（裁切後只讀字）
- **錨點確定性查表**：`venueService.resolveAnchors` 把讀到的字變成場域 + 出口 + 經緯度
- **出口示意圖**：`VenueMap` 讓使用者一眼確認或更正，出口編號歧義也在此化解
- **疏散重寫**：真實公尺距離取代九宮格棋盤距離

### 關鍵決策與理由

1. **系統裡從此只剩一種九宮格。** 場域九宮格整個移除，事件位置改以
   「場域 + 出口代碼 + 經緯度」表示。座標系混淆不是靠註解防範，是靠讓它不存在。
2. **AI 只讀字、不猜座標。** 「這根柱子在平面圖的哪一格」是模型不可能知道的事
   （它沒有平面圖）。位置由查表得出——確定性、可稽核。這讓「AI 不在生命安全
   資訊關鍵路徑上」這條原則在視覺定位上依然成立。
3. **裁切是整個機制的技術核心，不只是標註。** 整張 1024px 圖在 `detail:low`
   會被降到 512px，佔九分之一的出口牌只剩約 170px 寬、字高 20~40px，臨界可讀。
   改從**原圖**裁那一格（4000px 原圖 → 該格約 1333px）再縮到 1024px，
   字高可達 120px 以上。九宮格是讓低成本 OCR 真的讀得到字的前提。
4. **離線快照而非啟動時抓。** Overpass 是共用免費服務，不適合逐請求查詢；
   回報路徑上多一個外部依賴就多一個失敗模式。server 執行時完全不碰外部網路。
   （實測一次抓全台灣會連線中斷，因此改為分區查詢再合併。）
5. **地圖用示意圖，不用圖磚。** 一個圖磚視野 4~9 張、100~400KB，是整張態勢卡
   預算的 8 倍，在壅塞的地下網路上違反核心原則；OSM 圖磚亦有使用政策限制。
   而對「確認我在哪個出口」這個用途，街道幾何不增加任何資訊。
6. **粗略 GPS 不再被丟棄。** 舊版把 accuracy ≥300m 的定位整個視為不可信，
   但那個門檻答錯了問題：±300~500m 對「哪個月台」沒用，對「哪一站」綽綽有餘。
   這個訊號足以把 519 個場域收斂成 3~8 個點選目標——零打字的主路徑。
   順帶關掉了 v0.2 列為 Phase 2 的「GPS 反查場域」。
7. **疏散取「安全距離內最近的」，不是最遠的。** 初版實作排序取最遠，
   在台北車站會叫人往 620m 外的出口跑。安全距離是門檻，不是最佳化目標。
8. **停車場誠實降級。** 使用者要求涵蓋地下停車場，但實測 OSM 對它們只有
   一個帶名字的點：無出入口節點、無樓層標籤、名稱雜亂（甚至有錯字）。
   照做但標記 `exitsAvailable: false`，UI 自動降級——而不是產生一份
   看起來完整、實際上空的出口清單。

### 順手修掉的既有缺陷

- v0.2 的示範圖資站碼有錯且錯得安靜：`R09` 實為台大醫院（寫成台北101）、
  `BL13` 實為善導寺（寫成忠孝復興）、`R12` 實為 `R10`。手工維護圖資的代價。
- 轉乘站在 OSM 有多個節點（台北車站 = 北捷 BL12/R10 + 機捷 A1），
  不合併的話同一場火警會裂成兩個事件，直接打斷「同場域同類型 → 同一件」分群。
- `stationName` 過去退化成 `stationId`（server 不持有圖資）。現已由 server 解析。
- 建表與查表若各寫一套解析規則會出現「存的是 3、查的是 3號」這種安靜的比不中，
  因此抽出 `anchorParser.js` 給兩邊共用。

### 已知問題

- **`/api/vision` 仍無認證、無限流**，會轉發到付費 API。公開部署前必補（Phase 2）
- 出口編號在台北車站有三套並存（`M1~M8` 捷運、`Y9~Y22` 地下街、`1~5` 台鐵/高鐵），
  OCR 讀到裸數字時可能歧義 → 回傳多個候選讓使用者在示意圖上點，兩次點擊化解
- OSM 對台北捷運幾乎沒有 indoor mapping：多層站體（B1/B2/B3）無法區分
- 38 個捷運站在 OSM 沒有出口節點（多為台中線等高架站）→ 標記為無出口圖資
- 記憶體儲存重啟即清空（by design）

## v0.4.0 —— 真實地圖 + UI 重新設計（2026-09-04）

### 變更

- **地圖改為真實的 OpenStreetMap 底圖**（Leaflet）：可縮放、可點、有街景參照
- **事件位置三條路徑**：GPS（訊號好時）、地圖點選（永遠可用）、照片辨識（有牌子時）
- **UI 全面重新設計**：版面順序改為對應恐慌時的思考順序
- e2e 由 22 項擴充到 24 項（新增地圖選點驅動疏散的驗證）

### 關鍵決策與理由

1. **推翻 v0.3 的「示意圖就夠」判斷。** 當時的理由是圖磚太重（一個視野
   100~400KB，是態勢卡預算的 8 倍）。但那個理由算錯了成本歸屬——
   地圖在**回報端**，態勢卡預算是**讀取端**的約束，兩者不該互相綁架。
   更根本的是：示意圖回答不了「我到底在哪」。沒有街景參照，使用者無從判斷
   系統猜的位置對不對，而「確認」正是這一步存在的唯一理由。
2. **頻寬用動態載入解決，而不是放棄功能。** `React.lazy` 把 Leaflet 切成
   獨立 chunk（45KB gzip），只有展開「補充細節」的人才下載；首屏維持 55KB gzip
   （與加地圖前相同）。讀取端態勢卡完全不碰 Leaflet。
3. **底圖用 CARTO 而非 tile.openstreetmap.org。** OSM 官方圖磚的使用政策明文
   不供應用程式正式流量使用。CARTO 同樣是 OSM 資料（姓名標示照給），
   深色版也與本專案的深色 UI 一致。換回官方圖磚只需改一個常數。
4. **地圖可自由點選，不只能點出口。** 事件常常不在出口旁（月台中段、
   連通道）。新增 `incidentPoint` 欄位，疏散原點的優先序是
   **選點 → 出口錨點 → 場域中心**。
5. **GPS 設 60m 門檻。** 誤差大於這個值就只拿來收斂場域清單、不當事件位置——
   地下拿到的多半是過期快取，硬用會產生看似精確的錯誤位置。

### UI 重新設計的取捨

版面順序刻意等同恐慌時的思考順序：**我在哪 → 發生什麼 → （選配）補充 → 送出**。

- **主要動作固定在畫面底部**：恐慌中是單手操作，拇指構不到螢幕上半部。
  送出鍵永遠在 dock，捲到哪都按得到。
- **補充細節預設收合**：一次點擊就完成的回報是主路徑，
  地圖、語音、照片是給「還有餘裕的人」的，不該在首屏爭奪注意力。
- **四顆類型按鈕加上情境提示**（「煙、火、燒焦味」），
  恐慌中人不會逐字讀標籤，但會掃到關鍵詞。
- **嚴重度不只靠顏色**：實線框 vs 虛線框 + 文字徽章，色盲與強光下皆可分辨。
- 觸控目標最小 56px、關鍵動作 72px（濕手／手套／發抖時仍可命中）。

### 已知問題

- 圖磚仍是外部依賴：地下網路差時地圖可能載不出來
  （不擋回報——沒有地圖照樣能送出，只是位置停在場域層級）
- Leaflet 的 chunk 在極差的網路下可能載入緩慢，目前只有一行「載入地圖…」提示
- `/api/vision` 仍無認證、無限流

## v0.5.0 —— 移動威脅、無障礙疏散、離線殼、Android 感測器層（2026-09-04）

### 資料層：擺脫 Overpass

補方向地標需要上百次查詢，Overpass 公開實例只有 2 個併發槽，實測會被 429 與
連線中斷反覆打斷（跑 20 分鐘還跑不完）。改為**下載 Geofabrik 區域抽取檔在本機
解析**（`scripts/extract-osm.mjs`）：

- 全台灣 **101 秒**跑完，零限流，可任意重跑
- 能一次看到所有標籤，不必事先猜要查什麼——這直接促成了下面的無障礙功能
- 記憶體策略：兩趟讀檔（先抓 POI 縮範圍，再抓範圍內的節點與街道），
  座標打包成單一 Number。初版網格開太寬，在關西的密集都會區會超過
  JS Map 的 1670 萬上限而崩潰

成果：**778 場域 / 1340 出口**（含日本關西），方向地標覆蓋率 **23% → 96%**。

### 移動威脅追蹤（無差別攻擊：事件會跑）

原本的 `event.nearExitCode = report.nearExitCode` 只記得最新位置。這對火警沒問題，
對移動中的威脅是**危險的錯誤**：系統會把人往威脅前進的方向趕。

改為只追加不覆寫的錨點軌跡，由 `threatMotion.js` 做確定性判定。防誤判是重點：

| 判準 | 擋掉的情況 |
|---|---|
| 必須來自不同 session | **同一人邊走邊回報**（最可能的假陽性） |
| 間隔 ≥ 20 秒 | 多人同時回報同一件事 |
| 位移 ≥ 30m | 定位誤差 |
| 速度 0.3~6 m/s | 兩起獨立事件被誤併 |
| 多段方向發散 > 75° | 不硬給方向，改說「位置不一致」 |

疏散建議跟著翻轉：位於威脅前進方向（夾角 ≤70°）的出口一律進避開清單；
若所有出口都在前方，就誠實說「請尋找避難空間」而不是硬給一個方向。

速度上限初版設 3.5 m/s，實測把「95 公尺／21 秒」這種完全合理的奔跑誤判成
兩起事件——**攻擊者會跑**，已放寬到 6 m/s。

### 無障礙疏散（本次最有社會意義的功能）

標籤普查發現 OSM 的 `wheelchair` 覆蓋 42% 的出口，而且**沒有人拿它做疏散**。

關鍵事實鏈：
1. 火災時電梯不可使用（本專案的避難模板本來就寫著「勿使用電梯」）
2. 但捷運站裡**多數無障礙出口就是電梯**
3. → 火警 + 輪椅使用者 = 多數「無障礙出口」在此刻並不存在

國際官方準則對這個處境的建議是**前往避難空間待援**，而非前往出口。
所以這裡不是把清單過濾一下，而是**切換成性質不同的答案**：

```
府中站  推擠（電梯可用）→ 改往無台階可通行的 1 出口
        火警（電梯禁用）→ 無障礙出口需要電梯，火災時不可使用
                          請前往避難空間待援，讓周圍的人知道你的位置
```

安全預設：`wheelchair` 沒有標註一律視為**未知**，絕不當成可通行——
把「不知道」講成「可以」，對必須依賴這個資訊的人是會害死人的。

另加「有人無法自行疏散」一鍵標記，在態勢卡最顯眼處呈現——
知道哪裡有人需要協助，比知道事件本身更能決定救援資源怎麼派。

### Service Worker 離線殼

產品前提是「地下網路很差」，但先前的實作假設有網路。補上：

- 殼與資源 cache-first、場域圖資 stale-while-revalidate、態勢卡 network-first
- 送不出去的回報存進 IndexedDB，恢復連線自動補送（payload 本來就有 UUID
  冪等鍵，重送天然安全）
- 離線時態勢卡加 `X-NearPulse-Offline` 標頭，UI 誠實標示「這是上次取得的」

### Android app（`android/`，感測器層）

補上網頁做不到的那一層。**已實際編譯並通過 21 項單元測試、產出 7.6MB APK。**

- **氣壓計樓層偵測**：你在 B1 還是 B3。網頁完全拿不到這顆感測器。
  以「GPS 失去訊號的那一刻」為校正基準。
  ⚠️ 查證後確認**這不是原創**——Scientific Reports 2024 已有成熟演算法；
  我們的價值在於把它接到地下疏散與救援的用途上。
  同一份文獻指出既有研究**都未在深層捷運站驗證**，因為有 HVAC 加壓與
  **列車活塞效應**。對策是「取樣離散度大就不宣稱樓層」——在月台上寧可說
  「不確定」也不要說錯層數（已加測試涵蓋）。
- **人流停滯偵測**：不用感測器做定位（地下磁力計不可靠，沒有方位只有半徑），
  改偵測「從走動突然持續靜止」——那是推擠事故成形前的物理徵兆，
  而且完全不需要方位。絕不自動送出，只提示。

### 順手修掉的既有缺陷

- **態勢卡建構出錯會讓整個 server 崩潰**：批次迴圈沒有防護，一個 undefined
  就讓 Node 程序結束，連 POST /api/reports 都收不了。已包 try/catch，
  失敗時沿用上一張卡。
- 出口編號解析器只認台灣樣式，大阪梅田的 `G-1a`、`C-49`、`4-A` 全部解析失敗
- 無障礙篩選原本在「已被距離砍到只剩 3 個」的候選裡找，導致可通行的出口
  根本沒機會入選——**可通行的出口本來就稀少，篩選順序必須反過來**

### 已知問題

- **`/api/vision` 仍無認證、無限流**（Phase 2）
- opencode 免費層可讀中文站名（已實測），但延遲 34.5 秒且速率限制很緊 →
  只能配 deferred 模式；demo 當下可能撞到限流而走降級路徑
- 無障礙資料台灣覆蓋 42%、可做判斷的場域 100 個——夠 demo，不夠全面
- Android 的感測器邏輯有單元測試，但**未在真機驗證感測器讀值本身**

## v0.6.0 —— 事件分類依真實案例修正、百貨場域、鄰近警示（2026-09-05）

### 起因：使用者的兩個提問，其實是同一個故事

「百貨公司也有地下室，地圖沒有？」與「隨機殺人這種要歸在哪一類？」——
查證 2025 年台北無差別攻擊事件後發現，這兩件事是同一條路徑：

> 台北車站 **M 區出口的地下連通道**（投擲煙霧彈、持刀）
> → 移動至中山站外 → **誠品生活南西店**（百貨）
> 4 死 11 傷

這條路徑同時暴露三個缺口。

### 一、事件分類：新增「攻擊」

原本只有火警／急救／推擠／其他，持械攻擊只能歸「其他」——**門檻 3、
嚴重度 low**。這是嚴重的錯誤分類。對照台北捷運 11 年來的 5 起攻擊：

| 年 | 地點 | 傷亡 |
|---|---|---|
| 2014 鄭捷案 | 板南線**列車上**，龍山寺→江子翠密閉車廂 4 分鐘無處可逃 | 4 死 24 傷 |
| 2015 | 中山站 4 號出口附近 | 4 人受傷 |
| 2024 | 新埔站 | — |
| 2025 | 台北車站 M 區地下連通道 → 中山站 → 誠品南西（**移動**） | 4 死 11 傷 |

三個設計含意，全部實作：
1. **門檻改為 2**（與火警同級）——攻擊擴散最快，不能等湊 3 個人
2. **攻擊者會移動**——這正是 threatMotion 存在的理由
3. **建議本質不同**：不是「往出口疏散」而是「遠離、不要圍觀、找掩蔽」
   （參考 Run / Hide / Tell 通則）。把攻擊套用一般疏散文案會把人往危險推

### 二、在列車上（onTrain）

鄭捷案發生在行進中的車廂裡。對車廂內的人講「往 3 號出口」毫無意義。
新增 `onTrain` 旗標，疏散計畫切換成第三種性質的答案：

```
往其他車廂移動並遠離加害者，按下車廂內的緊急對講機通報司機員。
列車進站前不要嘗試開門；到站後立刻下車並遠離月台。
```

### 三、鄰近場域警示

事件以場域為單位聚合，所以攻擊者移動到下一個場域時會成為「另一起事件」——
但下一個場域的人**現在**就該知道。

刻意**不合併事件**（誤併兩起獨立事件的代價太高），只把警示擴散出去：
「約 800 公尺外的台北車站有進行中的攻擊事件 · 且正在移動」。
只對**已確認**的高嚴重度事件這麼做——擴散未經確認的警示會製造恐慌。

### 四、百貨／購物中心場域

先做資料查證再決定範圍：

```
building:levels:underground   全台 1724 個元素帶此標籤
有地下樓層的公眾零售場所      35 個（新光三越 B6、京站 B6、遠東SOGO B4…）
地下建物有標出入口的比例      僅 7.6%
```

所以百貨只建到**場域層級**（同停車場），`exitsAvailable=false`——
可以回報「在新光三越」，但沒有出口級定位與疏散路線。誠實標記，不假裝有。
`undergroundLevels` 仍有價值：它界定場域的垂直範圍，也是 Android 版
氣壓計樓層偵測的對照基準。

全台加日本共 **58 個**百貨／商場場域，總場域數 778 → 836。

### 順手修掉的既有缺陷

- **場域 ID 撞號**（使用者實測回報）：R14 同時是台北圓山與高雄巨蛋，
  K01~K10 是神戶海岸線與京都烏丸線。路線代碼只在同一城市內唯一，
  併入多城市資料後 findVenue 回傳錯的場域——使用者選了圓山卻顯示巨蛋。
  修法：ID 加路網前綴（座標劃分區域）、同區域撞號再附加名稱雜湊、
  **有歧義的別名一律拒絕解析**（查不到會逼使用者手選，那是安全的失敗；
  猜錯不是），建表加入唯一性檢查。
- 站況頁把整段疏散散文直接印出，恐慌中讀不完。改為 server 回**結構化 plan**、
  UI 排版；散文只留給語音。出口編號放最前面且放大——站內指標系統就是用
  編號導引的。
- 地圖改回**官方 OpenStreetMap 圖磚**（移除 CARTO）。
- SW 對 `/api/venues/nearby` 用 stale-while-revalidate，會讓使用者換地點後
  看到舊清單。改為 network-first。

e2e 40 → 48 項全數通過。

## v0.7 —— TDX 官方路網、目擊位置回報、態勢卡地圖（2026-09-05）

### 目標

回答兩個先前答不出來的問題：**車廂裡的人還要撐多久**，以及
**下一站的人現在該做什麼**。並讓態勢卡除了文字之外，也能用地圖看懂空間關係。

### 開發範圍（完成）

- **TDX 官方資料**（`scripts/fetch-tdx.mjs`，離線快照）
  - `StationExit` 437 筆：出口設施旗標與官方方位描述 → 北捷無障礙覆蓋 42% → **100%**
  - `S2STravelTime` 173 段：官方站間行車秒數
  - `StationOfRoute` 22 條**有方向的**站序 → 「下一站」的依據
  - `build-venues.mjs --network-only`：路網與 OSM 場域解耦，更新從數十分鐘變成幾秒
- **`services/trainService.js`**：`nextStations()` / `arrivalForecast()`
- **態勢卡**：`arrival`（車廂內）與 `inboundAlerts`（下一站月台）
- **`components/IncidentMap.jsx`**：唯讀 OSM 地圖，事件點 ✕ + 避開範圍圓 + 去處/避開出口
- **回報頁**：「事件在列車上」改為僅捷運場域可見；勾選後問「下一站是？」
- **確認流程第三問（`step: 'sighting'`）**：現場目擊者一鍵指認歹徒位置

### 關鍵決策

**不問方向，問下一站。** 恐慌中「往哪個方向」是抽象問題（往東？上行？）。
「下一站是哪一站」是車廂顯示器正在跑的字、廣播正在唸的詞，抬頭就能回答——
而在捷運路網上，「目前站 + 下一站」唯一決定了方向，資訊量完全相同。

**價值在月台，不在車廂。** 車廂裡的人做不了什麼；能改變結果的是下一站月台上的人：
門一開就讓開，不要照平常擠著上車。所以真正的產出是 `inboundAlerts`，
而它刻意只對**已確認的高嚴重度事件**發出——未經確認的警示擴散到整座月台，
製造的推擠風險可能大過它避免的風險。

**歹徒動態要有回報管道，不能只靠「再送一次完整回報」。**
移動判定的原料是「(時間, 錨點, 目擊者)」三元組，而在此之前這些三元組只能從
新回報取得——一個剛答完「有，我看到了」的現場目擊者，明明是全系統最清楚
歹徒位置的人，卻要重走一次回報流程才能說出來。那等於沒有管道，
「移動威脅追蹤」也就只是個伺服器端的能力，不是使用者用得到的功能。

第三問和前兩問有三點本質差異，都是刻意的：
**不是投票是觀測**（同一人可回報多次，歹徒會一直移動）、
**不影響事件狀態**（看錯位置不該讓事件被取消）、
**仍要求在場**（軌跡會變成疏散方向建議，不在現場的人「覺得他往那邊跑了」
會直接污染它——這是最不能放寬的一道）。

出口清單依「離威脅上次已知位置」由近而遠排序。台北車站有 27 個出口，
1、2、3 號的地標全是「往市民大道」——平鋪成一長串時，恐慌中根本挑不出來。
而人不會瞬移，用上次已知位置排序後，常見情況就變成第一或第二個就是。

**不猜車廂編號，但找到了可行的替代。** 使用者問「哪個車廂離樓梯近」，
並指出日本似乎有這種資料——這個直覺是對的，日本的乗換案内確實有「何号車が便利」。
但查證後確認**那不是開放資料**：

- ジョルダン 2022-09-30 新聞稿明載，資料是向**株式会社ナビット購買**的
  人工實地調查成果（就是車站裡「のりかえ便利マップ」海報那家公司）
- ODPT v4 的 24 個 endpoint 沒有月台設施或乘車位置；東京メトロ 舊 API
  已於 2022-03-31 關閉，遷移後出入口與站內設施資料並未保留
- TDX 整份 spec grep「月台門」「車廂位置」皆 0 命中
- OSM 的 `railway:platform:section` 全球僅 3098 筆、約 91% 在德語區，
  日本 0、台灣 0
- 台北捷運Go 有此功能（2024-07-14 北市府新聞稿），但資料不在 30 個開放
  dataset 也不在 TDX，需另行申請北捷 API

所以改用**開門側**（政府開放資料 128416 的 `Doors_Open_Side`）：
知道下一站往哪側開門，就能在到站前先移動到正確的那一側。它不需要知道
車廂編號就成立，而且是官方逐站資料。

這裡有個一開始擔心錯的地方：「左側開門」看似與行進方向有關（島式月台的
兩個方向從車內看應該相反）。實際查資料後發現**北捷靠右行駛**，所以島式月台
對兩個方向都在左側、側式月台都在右側——開門側確實與方向無關。119 站裡
只有 16 筆需要分方向（古亭、西門、東門這類疊式月台或跨月台轉乘站），
而那些資料裡明確寫了終點站名。e2e 用西門（兩個方向開門側相反）守這條線。

另外取 `Reserved_Spaces_for_Wheelchairs`：輪椅席在第幾節車廂——
這是**唯一**官方公開的車廂級資訊，對無障礙疏散直接有用。

**態勢卡只放絕對到站時刻。** 剩餘秒數每秒都不同，寫進卡片會讓每次輪詢的 ETag
都不一樣，弱網下最寶貴的 304 就永遠不會發生。改放 `arriveAt` 後卡片保持位元組相同，
倒數由 client 自算——順帶還能每秒更新，而不是跟著 12 秒輪詢一跳一跳。
e2e 有一項專門守這條線。

**地圖是補充，不是替代。** 態勢卡的前提是弱網優先（整張卡 <50KB），
而一個地圖視野是 4~9 張圖磚加 leaflet 約 150KB。所以地圖預設收合、
`React.lazy` 動態載入、切成獨立 chunk；文字敘述在任何情況下都先到且獨立可用。

**圓圈畫的是「系統避開的範圍」，不是「危害影響範圍」。** 後者需要現場的樓層、
通風與煙流資料，我們一樣都沒有。說明文字照這個意思寫，不寫成「影響範圍」。

### 修掉的錯誤

- **跨城市撞號在路網建表復發**：台北車站的「下一站」跑出高雄車站——`R11`、`R21`
  在北高兩地都有效，而我在 `buildNetwork` 裡自己寫了一份 alias 表，沒沿用
  `venueService` 的歧義排除規則。修法：限定營運機構的命名空間 + 沿用歧義排除，
  並加上**相鄰站距離健檢**（>5km 即排除該路線並讓 build 失敗），
  讓這類錯誤以後在建表時就爆出來。
- **`RouteID` 不唯一**：`BL-1` 同時是「頂埔→南港展覽館」與反向兩筆，
  用 RouteID 反查永遠拿到第一筆，導致反向路線的站序索引被套到正向路線上
  （台北車站的下一站變成隔五站的國父紀念館）。改存 routes 陣列的位置。
- **`StopTime` 不該算進到站時間**：台北車站→西門是 RunTime 120 + StopTime 42，
  加起來會多算 42 秒。對車廂裡等著開門的人，那是完全不同的一段時間。
- **「事件在列車上」出現在百貨公司**：改由 server 回的 `nextStations` 是否為空決定，
  非捷運場域整個選項隱藏。
- **e2e 三項期望過時**：TDX 的官方方位描述取代了 OSM 推導的「成功高中」，
  且測試用 `stations[0]` 索引會被其他事件位移。改為指名 station id、
  並直接驗 `plan.origin` 而不是繞著地標字串猜。

### 驗證

`server/test/e2e.sh` **71 項全通過**（原 48 項 + 列車與地圖幾何 13 項
+ 開門側 3 項 + 目擊位置回報 7 項），不需任何 API 金鑰。

## v0.6.1 —— 語音輸入修復與讀取端框線整併（2026-09-05）

### 修掉的錯誤

**語音輸入完全收不到字（回歸缺陷）。** 「自己描述」與「補充」兩處的麥克風
都是靜默失效——按下去、講話、放開，輸入框裡什麼都沒有。三個原因疊在一起：

1. **`SpeechRecognition.start()` 是非同步的。** 要開麥克風、要跟辨識服務
   建立連線，`onstart` 通常在 200~800ms 之後才發生。當時的實作是
   「按住說話」：`onPointerDown` 開始、`onPointerUp` 結束——而一次自然的
   點按只有 100ms 上下，等於在麥克風真正開起來以前就呼叫了 `stop()`。
   結果是**每一次**都收不到任何結果，不是偶爾失敗。
2. **`onPointerLeave` 會中斷。** 手指在 84px 的圓鈕上稍微移動一下就離開，
   講到一半直接斷線。
3. **麥克風鈕被包在 `<label>` 裡。** 那個 label 同時包著地點描述的
   `<input>`，所以點麥克風也會聚焦輸入框、彈出鍵盤——版面一位移，
   手指就離開按鈕，觸發第 2 點。

改成**點一下開始、再點一下結束**（也就是 STATUS 一直寫著的那個行為），
並把麥克風鈕移出 `<label>`。另外三個補強：

- **stop 先排隊**：使用者在 `onstart` 之前就按了停止，記下來，等真的開起來
  再停——否則早期的停止請求會落空，錄不到也停不掉。
- **`continuous = true` + 自動接回**：Chrome 在一段靜默後會自己結束。
  使用者還沒喊停就把它接起來，否則「呃……在……B1」中間停一下就斷線。
  跨越 restart 的定稿累積在 `finalText`，前半句不會掉。
  以 25 秒保險絲與 8 次接回上限收斂（無聲時 Chrome 會一直結束）。
- **失敗有原因可講**：沒權限、沒網路、非 HTTPS 是完全不同的三件事。
  原本一律靜默，使用者只會覺得「這功能壞了」。現在各講各的，
  而且每一句都以「請直接打字」收尾——打字永遠是走得通的那條路。
  非安全來源（`http://192.168.x.x`）先擋下來：那時 `SpeechRecognition`
  物件存在但 `start()` 直接吐 `not-allowed`，不先判斷就講不出原因。

語音輸入的定位不變：**加速器，不是必經路徑**。以上任何一項失敗都只是回到打字。

### 讀取端：把框線還給該被強調的東西

**事件頁籤看不出是哪一件事。** 一個頁籤只有一個 16px 圖標——火警與攻擊
在那個尺寸下形狀差異幾乎消失，而且完全看不出是哪一個場域。使用者只能
一個一個點開才知道自己在看什麼，等於把「掃一眼」變成「試誤」。
改成直接寫出「類型 + 場域名」，圖標退為輔助；當前那一則用實心標示牌強調，
未確認的用虛線框（不只靠顏色）。上方補一行「目前有 N 件事——你在看第 M 件」。

**框太多，等於沒有框。** 「你在哪」「無台階」「範圍篩選」「展開地圖」
「周邊訊息」原本各是一張有邊框的卡，五層框疊在事件之前，每一層都在喊
「我是一個獨立區塊」——結果是真正的主體（事件卡）被擠到第二屏。
它們其實是同一類東西：**看事件之前的設定**。合併成一張面板：外框一層，
列與列之間 1px 細線。總覽地圖與周邊訊息併成同一列的兩個入口（性質相同，
都是「還想多看一點」的收合開關）。

周邊訊息展開後同樣併成一個框：鄰近警示與已解除的左側色條拿掉，語氣改由
圖標與標題顏色承擔。**唯一保留實心紅牌的是事故列車進站警示**——那是
時效以秒計的事，其餘兩種是背景資訊，不該長得像另一則警報。

這與 v0.4 拿掉事件卡外框是同一條理由：框留給真正要強調的標示牌。
